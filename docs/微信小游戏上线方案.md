# 《星陨战线》上线微信小游戏：方案、计划与优化清单

> 评审对象：`D:\99-agent`（Three.js r158 + 原生 DOM UI，约 7,700 行，卡面素材来自第三方游戏）
> 目标：从「双击 index.html 的本地 3D 塔防」变成「可审核上线、能在中低端安卓机上稳定 30fps 的微信小游戏」
> 结论：**技术上能上，但不是一个"打包"动作，而是一次渲染层 + UI 层的重写。** 真正的长杆是版权和版号，不是代码。

---

## 0. 三个必须先拍的决定

### D1 · 走「小游戏」而不是「小程序」

小程序是 WebView + 逻辑层/渲染层分离，跑 3D 会被双线程通信拖死；小游戏是原生 Canvas + WebGL，逻辑与渲染同线程，才是 3D 的正路。

- 注册时服务类目选**游戏**，产物是 `game.json` + `game.js`，不是 `app.json` + `pages/`。
- 小程序做游戏类目一样要版号/备案，没有任何合规上的便宜可占。

### D2 · 首发横屏，但 UI 写成可重排

| 方案 | 优点 | 代价 | 判断 |
| --- | --- | --- | --- |
| **横屏（推荐首发）** | 你现在 16:9 的战场、3 张横排卡牌、HUD 三段式布局全部保留；3D 塔防横屏是行业惯例（明日方舟/王国保卫战） | 微信休闲用户单手持机，横屏需要双手 | 改动最小，先上线验数据 |
| 竖屏 | 微信小游戏主流形态，单手、分享卡、买量素材都更友好 | 战场要重排、相机俯角要拉、卡牌改横滑、HUD 重做，多 3–4 周 | 放 V1.1 做 A/B |

**落地做法**：`game.json` 里 `"deviceOrientation": "landscape"`；但 UI 底层用**相对布局**（百分比/锚点）而不是绝对像素，这样后面切竖屏只改断点和相机。

### D3 · 首发只做 IAA（广告变现），版号之后再谈 IAP

- 纯广告变现（无内购）**不需要版号**，门槛只有：软著 + 游戏自审自查报告 + 小程序/游戏备案。个人主体也能上。
- 一旦做内购就必须有版号，且个人主体不能上架收费游戏。版号 3–8 个月且不确定，**绝不能成为首发阻塞项**。
- iOS 端虚拟支付 2025 年 11 月才刚开放，且要进「小程序合作伙伴计划」、抽成 15%–30%。首发别碰。

## 1. 可行性体检：你离上线差多远

| 维度 | 现状 | 小游戏要求 | 差距 |
| --- | --- | --- | --- |
| **包体** | 未压缩约 **5.1 MB**（卡面 3.89 MB + three 0.65 MB + 代码 0.31 MB + UI 图 0.07 MB） | 主包 ≤ 4 MB，主包+分包 ≤ 30 MB | 必须做资源压缩 + 分包 |
| **UI** | 100% DOM：HUD、商店卡、选中面板、融合页、指南、结算、飘字、toast 全是 `document.createElement` + CSS | 小游戏**没有 DOM、没有 CSS** | **最大工作量**：整套 UI 要重写成 Canvas |
| **音频** | Web Audio 实时合成（振荡器 + 滤波器），4 种 mood | `InnerAudioContext` 只能放文件；`WebAudioContext` 是 Beta，Android 灰度 | 程序化配乐要**离线烘焙成文件** |
| **输入** | `pointerdown/pointermove` + raycaster | `wx.onTouchStart/Move/End` | 需适配层；且要好用得多（拖拽） |
| **后处理** | Bloom + ACES + 色差 + 暗角 + 颗粒 + 调色，多 pass | 移动 GPU 带宽极贵 | 低配必须关掉，高配半分辨率 |
| **Draw call** | 每个 3D 少女 70–120 个独立 Mesh、敌人 25–40 个，**估算同屏 800–1,400** | 中端安卓 WebGL 200–300 就接近瓶颈 | **目标 ≤ 250（高）/ ≤ 120（低）**：必须合并几何体 |
| **分辨率** | DPR 封顶 1.4 | 建议 1.0（低）/ 1.25（中） | 直接改数值 |
| **字体** | 优先系统楷体 / 微软雅黑 | 手机上这两个字体**不存在**，会 fallback 成黑体 | 标题字体要子集化打包 |
| **存档** | `localStorage` 只存了静音 | `wx.setStorageSync` | 顺手做局中存档 |
| **素材版权** | 卡面来自《Yokai Art》第三方游戏 | 审核要求原创或授权 | **红线，见下一节** |

一句话：**代码量不是问题，架构才是问题。** 现在的 `game.js` 把「玩法 / DOM UI / 3D 场景」焊在一起，直接塞进小游戏会碎。

## 2. 两条红线（不解决，后面全白做）

### R1 · 卡面素材必须换掉

你在 README 和 `THIRD_PARTY_NOTICES.md` 里写得很清楚：12 张角色卡面 + 部分卡框来自《Yokai Art: Night Parade of One Hundred Demons》。

- **这是审核必查项**，也是上线后被投诉下架/索赔的高风险项。微信对"盗用他人游戏素材"的处理是下架 + 封号，不是警告。
- 你的 3D 模型是**自己程序化生成的**（`art.js`），这才是可主张的原创资产。
- **最省钱的替代方案**：既然 3D 少女已经做出来了，就用 `art.js` 的模型离屏渲染出 I/II/III/IV 四阶段立绘 —— 一条脚本渲染 12 张 512×768 的 PNG，风格还和游戏内完全一致。你的 `PostFX` + 角色工厂已经具备这个能力，成本 1–2 天，且彻底解决版权问题。

> 这条同时解决包体：12 张自制图可以按需压到 ~40 KB/张。

### R2 · 资质时间线（并行启动，别等代码写完）

## 3. 技术方案

### 3.1 四条路的对比

| 方案 | 说明 | 工作量 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| **A. three.js + 自研 Canvas UI** | 保留 3D，UI 全手写 2D 绘制 + 命中检测 | 高（UI 要造轮子） | 布局代码多、后期难改 | 不推荐 |
| **B. three.js + `minigame-canvas-engine`** ⭐ | 微信官方轻量 Canvas 布局引擎，支持类 CSS（flex/圆角/九宫格/伪类），3000+ 小游戏在用 | 中 | 生态小、复杂动效要绕 | **推荐** |
| **C. 迁到 Cocos Creator 3.x** | 引擎成熟、一键导出小游戏、性能工具全 | 极高（程序化建模全部重写） | 3D 场景是代码生成的，不是 glTF，等于重做美术 | 不现实 |
| **D. Unity / 团结引擎导出** | 工具链最好 | 极高 | 没有 Unity 资产，包体大 | 不现实 |

### 3.2 推荐架构

```
minigame/
├─ game.js                # 入口：启动流程、生命周期、存档
├─ game.json              # deviceOrientation: landscape
├─ platform/              # 平台适配层（唯一直接调 wx.* 的地方）
│   ├─ input.js           #  touch → 归一化的 pointer 事件
│   ├─ audio.js           #  InnerAudioContext 池 + 音量/静音
│   ├─ storage.js         #  wx.setStorageSync / 存档结构
│   ├─ ad.js              #  激励视频：预加载、show、失败重试
│   ├─ share.js           #  shareAppMessage / onShareTimeline
│   └─ lifecycle.js       #  onShow/onHide 自动暂停、切后台恢复
├─ core/                  # 从 game.js 抽出的纯玩法（不碰 DOM、不碰 three）
│   ├─ run.js             #  一局状态机：布防/波次/结算
│   ├─ combat.js          #  攻击、伤害、状态、击杀
│   ├─ economy.js         #  金币产出/消耗（含 P0 的升级出口）
│   └─ mods.js            #  铭文结算
├─ render/                # three.js 场景（web 与小游戏共用）
│   ├─ adapter.js         #  three.js 的小游戏兼容层
│   ├─ scene.js / world.js / art.js
│   └─ quality.js         #  三档画质 + 动态降级
└─ ui/
    ├─ layout/            #  canvas-engine 的 XML 模板（对应现在的 index.html）
    ├─ theme.css          #  从 main.css 摘出来的子集
    └─ overlay.js         #  血条、飘字、射程圈（2D 直接绘制）
```

### 3.3 关键技术点

**1）three.js 怎么跑起来**

小游戏没有 `document` / `window` / `Image`。用适配层补：

- 现成方案：[Three.js Platform Adapter](https://three.minisheep.cn/guide/)（rollup/vite 插件，自动处理 worker/wasm/分包，覆盖 300+ 官方示例）；
- 或用官方 `weapp-adapter` 思路自己写 200 行 shim。
- three.js **r158 仍支持 WebGL1 回退**（WebGL1 在 r163 才移除），所以老安卓也能跑——这点你不用升级版本。

**2）UI 怎么合成到一屏**

小游戏只有**第一个** `wx.createCanvas()` 是上屏的，之后创建的都在离屏。

```
[上屏 Canvas] ← WebGL (three.js) 渲染 3D
      ↑
      └─ 一个全屏 quad（OrthographicCamera），贴图 = UI Canvas
[离屏 Canvas] ← canvas-engine 渲染 HUD/商店/面板；血条和飘字也画在这
```
UI Canvas 只在「有变化」时重绘并 `texture.needsUpdate = true`，静止时不产生开销。这样 1,600 个 DOM 元素变 1 张纹理，draw call 只多 1。

**3）音频：把程序化音乐"烘焙"出来**

你现在 `audio.js` 用振荡器实时合成。手机上：
- `InnerAudioContext` 播放短音效有 100–200ms 延迟，打击感会废掉；
- `WebAudioContext` 是 Beta，Android 灰度，不能作为首发依赖。

**做法**：写一个 `tools/bake-audio.mjs`，在 Node/浏览器里用 `OfflineAudioContext` 跑一遍 `audio.js`，导出：
- 4 段 BGM（build / battle / boss / menu），各 40–60s 无缝 loop，96kbps 单声道 mp3 ≈ 500–700 KB；
- 20 个 SFX，各 0.1–0.6s，mp3/ogg ≈ 5–15 KB。

产物放**分包或 CDN**，不占主包。这步几乎零成本，且音质比实时合成更稳。

**4）首屏 3 秒**

微信用户的等待阈值是 3 秒，每多 1 秒流失 ~10%，6 秒后流失 50%。

| 阶段 | 内容 | 预算 |
| --- | --- | --- |
| 首屏（主包） | 纯 Canvas 画的 Logo + 进度条 + "点击开始" | ≤ 800 KB |
| 点击后 | 加载 3D 依赖 + 首关资源（分包异步） | ≤ 2 s |
| 进战斗 | 卡面/音频按需加载 | 后台静默 |

分包策略：`subpackage-cards`（12 张卡面）、`subpackage-audio`（BGM+SFX）、主包只留 three + core + 首屏 UI。分包异步化基础库 ≥ 2.10.4。

**5）资源压缩账**

| 资源 | 现状 | 处理后 | 手段 |
| --- | --- | --- | --- |
| 12 张角色卡面 | 3.89 MB | ~500 KB | 512×768 WebP q80（显示宽度约 200–280 px，2 倍图足够） |
| three.min.js | 652 KB | ~160 KB（gzip 后） | 代码包传输自带压缩 |
| 游戏代码 | 307 KB | ~90 KB | 混淆压缩 |
| UI 图 | 68 KB | 68 KB | 合并成 1 张图集 |
| 字体 | — | ~150 KB | 只子集化 UI 里出现的 ~400 个汉字 |
| **主包合计** | **5.1 MB** | **~1.0 MB** | ✅ |

## 4. 分阶段计划（1 人全职，共 8–10 周）

> 若兼职，整体 ×1.5–2。资质并行推进，不占开发时间。

### W0（第 1 周）· 决策 + 资质 + 技术验证

| 事项 | 产出 | 验收 |
| --- | --- | --- |
| 注册小游戏账号（选企业/个体户，为后续 IAP 留路） | 账号 + AppID | 能建工程 |
| 提交软著、准备自审报告 | 受理回执 | 已提交 |
| **技术 Spike**：小游戏里跑起 three.js，加载现有场景 + 8 个 3D 少女，真机测帧率 | 一张机型帧率表 | 拿到真实数据再决定砍什么 |
| 测试机 | 红米 Note 11 / OPPO A 系列 / iPhone 8 | 三台在手 |

> **这是全项目最重要的一周。** 如果中端机连 20fps 都不到，方案就要改成"低模 + 精灵敌人"，整个排期重来。别跳过。

### W1–2 · 平台层 + 工程骨架

- 建 `minigame/` 工程，接 `game.json`、启动流程、`platform/*` 适配层。
- `core/` 抽取：把 `game.js` 里的玩法逻辑（波次、经济、战斗、融合）从 DOM 调用里剥出来。
- UI 骨架：用 canvas-engine 复刻 **HUD + 商店 + 选中面板** 三个高频界面。
- 验收：能在真机上放塔、打第一波、看到血条和金币变化。

### W3–4 · UI 全量迁移 + 横屏适配

- 复刻剩余界面：融合三选一、阶位升华、结算、指南、暂停。
- 安全区：顶部避让胶囊按钮（右上 87×32 px + 边距），刘海屏 `safeArea`。
- 飘字/血条改为 2D overlay 统一绘制（同时干掉 2 draw call/敌人）。
- 验收：一局从开始到结算，**没有一处 DOM**，全流程可玩。

### W5–6 · 性能专项（决定生死）

- 几何体合并、材质共享、画质三档、动态降级、对象池。
- 目标：中端安卓 **30fps 稳定**，低端 ≥ 24fps，iPhone 8 ≥ 40fps。
- 验收：三台测试机各跑 10 分钟，`wx.getPerformance` 采样 FPS 曲线无长掉帧。

### W7 · 留存与变现

- 激励视频（复活/双倍/重掷）、分享、好友排行（开放数据域）、每日挑战、签到。
- 埋点接入（`wx.reportAnalytics`）。
- 验收：广告能拉取、能展示、能发奖、能兜底失败。

### W8 · 测试 + 提审

- 真机矩阵回归、断网/切后台/来电中断测试、低内存测试。
- 首次提审，预留 **2–3 次驳回** 的时间（内容、类目、隐私、素材是最常见原因）。
- 验收：审核通过，进入灰度。

### W9–10 · 灰度 + 数据迭代

- 分阶段发布（1% → 10% → 50% → 100%）。
- 看 D1 留存、首局完成率、波次流失点、广告观看率。
- 用数据决定 V1.1 是加内容还是改留存。

## 5. 性能优化清单（按 ROI 排序）

| # | 项 | 现状 | 目标 | 做法 | 收益 |
| --- | --- | --- | --- | --- | --- |
| 1 | **几何体合并** | 每少女 70–120 个 Mesh | 每少女 12–18 个 | 用 `BufferGeometryUtils.mergeGeometries` 把静态部件（躯干/裙/底座/光环）按材质合并，只保留头/双臂/武器/翅膀/尾为独立动画节点 | draw call ↓ 70% |
| 2 | **敌人降级** | 25–40 Mesh/只 | 高配 8 Mesh；低配 1 个 billboard 精灵 | 低配直接把敌人换成朝向相机的序列帧/单帧精灵 | draw call ↓ 60% |
| 3 | **关实时阴影** | 场景 + 角色大量 `castShadow` | 低/中配关闭 | 用已有的 blob 阴影（`game.js` 里的 tower.shadow）或烘焙到地面 | 每帧省 1 次 shadow pass |
| 4 | **后处理分级** | 6 个 pass 全开 | 低：全关；中：半分辨率 Bloom；高：保留 | 低配用 additive sprite 假辉光替代 Bloom | 带宽 ↓ 50%+ |
| 5 | **DPR 分级** | 1.4 | 1.0 / 1.25 / min(dpr,1.5) | `renderer.setPixelRatio` | 填充率 ↓ 50% |
| 6 | **血条/飘字改 2D** | 每敌人 2 个 Plane + 每帧 quaternion | 0 个 3D 对象 | 画到 UI Canvas 上，批量 `fillText` | draw call −30，GC − |
| 7 | **粒子对象池** | 每次 burst `new` 一堆 | 池化 | `vfx.burst` 内部复用数组 | 减少 GC 卡顿 |
| 8 | **逻辑减负** | `updateEnemies` 里每帧 `filter` + 大量 `new Vector3` | 复用临时向量、缓存 aura 列表 | 每帧分配归零 | JS 时间 ↓ |
| 9 | **降级策略** | 无 | 30 秒平均 FPS < 26 → 降一档 | `quality.js` 自动降级（关 Bloom → 关阴影 → 降 DPR → 减粒子） | 兜住低端机 |
| 10 | **同屏上限** | 无 | 敌人 ≤ 12（低）/ 20（高） | 波次队列延迟出场，不是简单丢弃 | 稳定性 |

**性能预算（写进团队的硬指标）**：

| 指标 | 低配 | 高配 |
| --- | --- | --- |
| FPS | 30（允许 24） | 60（允许 45） |
| Draw call | ≤ 120 | ≤ 250 |
| 三角面 | ≤ 60k | ≤ 150k |
| 同屏敌人 | 12 | 20 |
| 粒子 | 150 | 400 |
| 纹理内存 | ≤ 40 MB | ≤ 80 MB |
| 每帧 JS（逻辑） | ≤ 6 ms | ≤ 8 ms |

## 6. 玩法与 UX 的小游戏化改造

小游戏的用户不是"玩家"，是"拿手机的人"。你现在这套是给桌面玩家设计的。

| # | 改动 | 为什么 | 具体做法 |
| --- | --- | --- | --- |
| 1 | **单局从 10–12 分钟压到 5–7 分钟** | 碎片化场景，长局 = 高流失 | 8 波 → 6 波；波间隙 14s → 8s；保留 3× 速；Boss 放第 6 波 |
| 2 | **拖拽部署替代两步点击** | 手机上"点卡→点法阵"极易误触 | 从卡片拖出幽灵塔，手指上方 120px 显示（避免手挡），松手即部署；点选也保留 |
| 3 | **热区放大** | 手指比鼠标粗 | 所有可点元素 ≥ 44×44 px；法阵拾取用不可见的大圆代理（世界半径 0.9） |
| 4 | **首局 90 秒内给第一个爽点** | 微信用户学习耐性极低 | 第 1 波 18 秒就到；首杀必暴击；第 2 波强制引导一次融合 |
| 5 | **失败缓冲** | 一次失败就流失 | 星核破了 → "看广告复活"（回 50% 结界 + 清屏），每局 1 次；首局免费送 1 次 |
| 6 | **信息前置** | 小游戏用户不看说明 | 上一轮评审说的"下一波预告"在小游戏里**从加分项变成必需品** |
| 7 | **随时可退可续** | 微信会随时切后台 | `onHide` 自动暂停 + 写存档；回来弹"继续远征" |
| 8 | **减少一次性教程** | 没人读长文 | 拆成 3 个不超过 8 字的气泡，跟着操作走 |
| 9 | **结算页即分享页** | 分享是最便宜的流量 | 评分 + "我守住了第 X 波" + 一键分享得星辉 |
| 10 | **横竖屏/分辨率回归** | 安卓碎片化 | 16:9 / 18:9 / 19.5:9 / 20:9 四档回归截图比对 |

## 7. 增长与商业化

### 7.1 广告点位设计（IAA 的核心是"点位密度 × 用户体验"）

| 点位 | 触发 | 奖励 | 频次限制 |
| --- | --- | --- | --- |
| 复活 | 星核归零 | 回 50% 结界 + 清屏 | 每局 1 次 |
| 双倍结算 | 结算页 | 星辉 ×2 | 每局 1 次 |
| 免费重掷 | 融合页重掷用完 | +1 次重掷 | 每日 5 次 |
| 开局补给 | 开局布防期 | +100 星币 | 每日 3 次 |
| 每日宝箱 | 主界面 | 随机星辉/皮肤碎片 | 每日 1 次 |

原则：**前 3 局不弹任何广告**（先让用户爱上），第 4 局再开点位；绝不打断战斗；失败时的广告是"救"不是"罚"。

### 7.2 分享与社交

- **结算分享**：带评级和波数的分享卡（`wx.shareAppMessage`），分享成功给星辉。
- **好友排行榜**：开放数据域 + `minigame-canvas-engine` 绘制（官方推荐组合，3000+ 游戏在用）。榜单维度：最高波数 → 最短用时 → 是否零漏怪。
- **朋友圈分享**：`wx.onShareTimeline`（需基础库 2.11.3+，且要开通）。
- **挑战码**：把一局的随机种子编码成短链，发给好友打同一套铭文。

### 7.3 留存钩子

| 钩子 | 说明 |
| --- | --- |
| 每日挑战 | 固定种子的同一局，每天一次，好友比分数 |
| 签到 | 7 天给星辉/皮肤碎片，第 7 天给"终阶抉择"解锁 |
| 星图（局外） | 用星辉解锁**内容**（新铭文池、困难档、无尽模式、配色），不解锁数值 |
| 收藏图鉴 | 已见过的敌人/铭文/阶段立绘，收集本身是留存 |

### 7.4 付费路径（版号之后）

只卖**内容与外观**，不卖强度：
- 角色皮肤（换色/换装，复用 `art.js` 换材质参数，成本极低）
- 章节 DLC（新地图 + 新波次）
- 去广告一次性买断

参考《守塔不能停》的教训：一旦卖数值，第二关就能卡死玩家，评价直接崩。

## 11. 上线 Checklist

**资质**
- [ ] 小游戏账号 + 游戏类目
- [ ] 软著（受理回执即可先提审）
- [ ] 游戏自审自查报告
- [ ] 小程序备案 / 游戏备案
- [ ] 隐私协议 + 隐私保护指引

**技术**
- [ ] 主包 ≤ 4 MB（目标 ≤ 1.5 MB）
- [ ] 首屏 3 秒内可点"开始"
- [ ] 三档画质 + 自动降级
- [ ] 中端安卓 30fps / 低端 24fps
- [ ] 切后台自动暂停 + 存档恢复
- [ ] 断网、来电、低内存不崩
- [ ] 安全区 + 胶囊避让（16:9 ~ 20:9 全部回归）
- [ ] 音频：BGM 循环无缝、SFX 延迟 < 100ms、可静音
- [ ] 无 DOM 残留、无 `localStorage`、无 `window` 依赖

**内容与合规**
- [ ] 卡面 100% 原创/授权
- [ ] 实名 + 防沉迷
- [ ] 广告点位有频次限制、不遮挡关闭键
- [ ] 分享图不含违规内容

**数据**
- [ ] 12 个埋点全通
- [ ] 崩溃与性能上报
- [ ] 后台能看留存/漏斗/广告

## 12. 最后一句

**这次移植的重点不是"让 3D 跑在手机上"，而是"让一个桌面游戏变成手机游戏"。**

三件事按顺序做，顺序错了会返工：
1. **先解决版权**（1–2 天，否则 10 周白干）；
2. **先验证性能**（W0 真机 Spike，否则架构选错）；
3. **先砍 UI 复杂度**（只做 3 个高频界面，别追求像素级还原）。

技术上你最大的敌人是 **draw call 和 DOM**，产品上最大的敌人是 **3 秒加载和 5 分钟单局**。
